# Noctivault 콘텐츠·수익화·자동화 통합 기획서

Version 2.2 | 수정일: 2026.10.19 | 장기 성장·운영 계획

실제 미해결 사건을 조용하고 깊이 있게 기록하는 영어 미스터리 다큐멘터리 채널.

# 01 프로젝트 목표와 운영 방향

| 항목 | 확정 방향 |
|---|---|
| 장기 목표 | 월 순수익 50만 원 수준의 지속 가능한 채널 |
| 현재 단계 | 구독자 약 40명, Shorts 평균 약 100회인 초기 성장 단계 |
| 주제 | 실제 실종 사건·역사적 미해결 사건, 검증 가능한 기록 |
| Shorts | 주 3편, 월 약 12~13편, 40~60초 목표 |
| Long-form | 월 1편, 한 사건을 깊게 다루는 약 30분 목표 |
| 채널 톤 | Shorts·Long-form 모두 차분한 남성 저음 다큐멘터리 |
| 생성 비용 | 월 $20 상한, 유료 재생성·재시도 포함 |
| 기술 방향 | NestJS CLI 워커 + GitHub Actions + FFmpeg + Supabase + GCS. 검수·공개·성과는 YouTube Studio |
| AI 영상 | fal의 Kling VIDEO 3.0 Standard, 무음 5초 재현 장면 |
| TTS 방향 | OpenAI onyx 유지. Qwen3-TTS 연결은 이번 범위에서 제외 |

월 50만 원은 장기 도달 목표다. 현재 조회수나 특정 개월 수를 근거로 달성 시점을 약속하지 않는다. 콘텐츠와 시청자층을 축적하면서 제작 안정화 → 성장 개선 → 수익화 → 지속 운영 순서로 발전시킨다.

Shorts는 신규 시청자 발견과 사건 흥미 유발, Long-form은 사건 이해와 몰입·시청 시간 확보를 맡는다. Shorts에서 Long-form으로 이동하는 효과는 실제 유입 데이터로 확인한다.

발행량은 운영 목표다. 근거·품질·예산 조건을 충족하지 못하면 해당 편을 보류한다. 롱폼은 자료가 충분할 때 약 30분으로 제작하고, 부족하면 길이를 줄인다.

# 02 브랜드 및 편집 원칙

- 채널 약속: “True Mysteries, Told Quietly.”
- 실종 피해자·가족을 존중한다. 자극적 표현, 잔혹한 묘사, 무근거 범죄 추측, 가짜 증언을 금지한다.
- 확인된 사실(Fact), 보도된 주장(Reported), 가설(Hypothesis), 미확인(Unverified)을 구분한다.
- 사건의 현재 상태를 확인하고, 이미 해결된 내용을 미해결처럼 소개하지 않는다.
- AI 재현 화면은 화면에 표시하고 설명란에도 알린다. 유튜브의 합성·변형 콘텐츠 신고 대상이면 업로드 설정에도 반영한다.
- AI로 증거 사진·공식 문서·실제 증언처럼 보이는 자료를 만들지 않는다.
- 롱폼은 잠들기 편안하되 정보가 충실해야 한다. 반복 대본·빈 화면·같은 클립 반복으로 시간을 채우지 않는다.

# 03 콘텐츠 포트폴리오와 사건별 확장

| 형식 | 콘텐츠 약속 | 제작 원칙 |
|---|---|---|
| Shorts | 단일 단서·마지막 행적·의문점 한 가지 | 첫 2초에 집중할 이유 제시, 한 편만 봐도 정보 가치 제공 |
| Long-form | 사건의 배경·연대기·수색·증거·현재 상태 | 검증된 자료에 기반한 맥락과 분석, 약 30분 목표 |
| 연계 | 같은 사건을 Shorts와 Long-form으로 연결 | 배경 정보 중첩은 허용, 실질적 확장 없이 재포장하는 것은 차단 |

롱폼 권장 흐름: 핵심 의문 제시 → 사건 전 배경 → 마지막 확인된 행적 → 수색과 증거 → 확인된 내용과 남은 질문 → 현재 상태. 도입과 각 구간의 길이는 자료와 시청 반응에 맞춰 조정한다.

예시: Shorts가 ‘마지막 확인 장소’를 다뤘다면 롱폼은 그 사실을 연대기 안에서 다시 설명할 수 있다. 다만 추가 기록·수색 과정·증거의 한계 등 충분한 새 정보를 제공해야 한다. 같은 50초 대본을 늘이거나 장면만 바꿔서는 새 콘텐츠로 보지 않는다.

# 04 사건 식별과 콘텐츠 중복 방지

사건이 같은 것과 콘텐츠가 중복인 것을 구분한다. 기존 발행 영상 전체를 영구 비교 대상으로 삼으며, 기간이 지났다는 이유로 중복 판정을 해제하지 않는다.

| 검사 계층 | 기준 | 결정 |
|---|---|---|
| 사건 식별 | canonicalCaseId, 날짜·장소·인물, 별칭, 외부 출처 ID | 같은 사건이면 기존 기록에 연결. 사건 ID 일치만으로 제작을 차단하지 않음 |
| 콘텐츠 식별 | caseId, format, angleId, editionId, 핵심 claimIds | 이미 예약·제작·업로드된 같은 콘텐츠의 신규 제작 차단 |
| 정보 중복 | 핵심 주장·대본·주요 단서·시청자에게 제공하는 가치 | 표현·제목·형식만 바꾼 재포장 차단 |
| 형식 간 확장 | Shorts의 사실을 포함하는 롱폼, 롱폼에서 파생한 Shorts | 독립적 정보 가치와 실질적 확장이 있으면 허용 |
| 업데이트 | 새로운 공식 발표·확인된 실질적 증거 | 이전 콘텐츠와 연결하고 사람 승인 후 별도 edition으로 제작 |

- 같은 사건의 롱폼은 기본 1편. 후속 보도는 새 검증 정보가 있을 때 업데이트로 취급한다.
- 같은 사건의 Shorts는 서로 다른 핵심 정보가 있거나, 롱폼의 특정 단서를 독립적으로 이해할 수 있게 설명할 때 허용한다.
- 공통 배경·이름·날짜가 겹친다는 이유만으로 중복 처리하지 않는다. 핵심 정보와 전달 가치가 같은지 판단한다.
- angleId·claimId를 새로 만들거나 표현을 바꾸는 것으로 중복 검사를 우회할 수 없다. 동의어와 같은 뜻의 주장을 기존 ID에 연결한다.
- 의미 판정이 모호하면 보류한다. 사람이 승인해도 출처 없는 정보나 단순 재포장을 허용하지 않는다.

통과 기준은 ‘기존 사건 재선정 0건’이 아니라 ‘승인되지 않은 중복 콘텐츠 발행 0건’이다.

# 05 영구 기록과 기존 데이터 활용

GitHub Actions의 실행 파일시스템과 캐시는 영구 이력으로 사용하지 않는다. Supabase를 콘텐츠 상태의 기준 저장소로 유지하고, 기존 published_topics 이력을 사건·콘텐츠 단위로 정리한다. NestJS는 작업 시 실행되는 CLI 워커로 사용한다. React 보드·PWA·HTTP 서버는 제거하며 PC 상시 실행이나 별도 관리 API 배포를 요구하지 않는다.

Git에는 코드·스키마·검증 규칙을 기록한다. 운영 상태를 Git과 Supabase에 각각 수정하는 이중 저장 구조는 만들지 않는다. Git 기반 상태 저장으로의 교체는 실제 운영 문제가 확인된 경우에만 별도로 검토한다.

| 기록 | 필수 내용 |
|---|---|
| CaseRecord | 사건 ID, 정식 이름, 별칭, 시기·장소, 출처, 현재 상태 |
| ContentRecord | contentId, caseId, format, angleId, editionId, 핵심 claimIds, 대본·검토본 hash, 상태, YouTube ID |
| ClaimRecord | 단위 주장, Fact/Reported/Hypothesis/Unverified 구분, 원문 근거·위치·확인 시각 |
| AssetRecord | 원본 URL, 라이선스와 확인 근거, 크레딧, AI 재현 여부, 사용 이력 |
| Run/BudgetRecord | runId, 작업 단계, 공급사 작업 ID, 비용 예약·실제 사용액·결과 불명 금액 |

기존 YouTube 업로드 목록과 DB를 대조해 누락된 영상을 가져온다. 과거 영상의 대본·각도를 복원할 수 없으면 검토 필요 상태로 남기고, 해당 사건은 사람 확인 없이 새로 발행하지 않는다.

DB 조회·상태 저장 실패 시 생성·발행을 중단한다. 현재 코드의 6개월 중복 검사와 오류 시 통과 동작을 먼저 교체한다. API 키·OAuth 토큰·불필요한 개인정보는 Git이나 공개 로그에 저장하지 않는다.

# 06 한 편을 만드는 표준 흐름

1. 최신 코드와 영구 이력을 읽고, 기존 업로드 및 미완료·결과 불명 작업을 확인한다.
2. 후보 사건을 정규화한다. 같은 사건이면 기존 caseId에 연결하고, 새 콘텐츠로서의 정보 가치와 중복 여부를 판단한다.
3. 최소한의 출처 확보 후 콘텐츠를 원격 DB에 예약한다. 유료 호출 전에 예상 최대비용도 예약한다. 예약에 실패하면 시작하지 않는다.
4. 공식 기록·신뢰할 수 있는 보도를 수집해 주장별 근거를 만든다. 출처가 없으면 LLM의 기억으로 사실 목록을 채우지 않는다.
5. 근거가 확보된 주장으로 대본을 생성한다. 제목·썸네일 문구·설명란도 함께 만든다.
6. 완성된 대본과 모든 게시 문구를 다시 검증한다. 새로 생긴 주장, 과장, 근거와 반대인 표현을 수정하고 재검증한다.
7. 검증본을 확정한 뒤 TTS·자산을 생성하고 FFmpeg으로 합성한다. 대본이 바뀌면 관련 검증·음성·자막도 다시 처리한다.
8. 업로드 직전 검증 문구·렌더 입력·보존 파일 hash와 자료 권리를 확인한다.
9. 비공개 업로드 후 영상 ID를 저장한다. 운영자가 YouTube Studio에서 실제 영상·음성·자막·출처·라이선스·AI 표시와 제한 안내를 확인하고 직접 공개하거나 예약 게시한다.
10. 워커가 YouTube의 실제 공개 상태를 조회해 published로 기록한다. 실제 비용·제작 시간은 따로 기록하고 성과는 Studio에서 확인한다.

이전 키워드 기반 ClaimGate와 구형 JS 제작 경로는 제거했다. 현재 경로는 기록된 원문·주장 대조와 생성 후 최종 검증을 사용하며 운영자의 실제 재생본 검토를 대신하지 않는다. 자동 공개 명령은 제공하지 않는다.

# 07 동시 실행과 장애 복구

- GitHub Actions의 채널 공통 concurrency 그룹을 사용한다. 로컬·다른 실행 경로도 DB의 원자적 콘텐츠 예약을 통과해야 한다.
- 같은 contentId를 재개할 때 자기 예약을 중복으로 오인하지 않는다. 다른 작업의 예약과 충돌하면 생성하지 않는다.
- 상태 흐름: reserved → draft → verified → rendered → uploading → uploaded_private → Studio에서 직접 공개 → 원격 조회 후 published. 재개 가능한 실패는 failed, 업로드 결과를 알 수 없으면 reconciliation_required로 구분한다. 기존 approved·publishing 기록은 새 공개 요청 없이 Studio 상태와 대조한다.
- 업로드 전에 uploading 상태를 원격 저장한다. runId/contentId만으로 YouTube가 중복 업로드를 막아 주는 것은 아니다.
- 응답 유실·영상 ID 저장 실패 시 자동 재업로드하지 않는다. 저장한 요청 정보·시간·메타데이터와 채널 업로드 목록을 대조하고, 일치 여부가 불명확하면 사람 확인을 기다린다.
- Studio 공개 여부는 기존 영상 ID로 조회하고 새 영상을 올려 복구하지 않는다. 공개 이후 다시 비공개로 전환해도 과거 제작 이력은 유지한다.
- 업로드 전 원고·자료가 바뀌면 검증·렌더를 다시 수행한다. 업로드 후 Studio에서 변경한 문구는 원래 검증 원고에 자동 반영되지 않으므로 운영자가 변경된 주장·근거를 직접 검토한다.
- 대본·음성·렌더 결과 등 재개에 필요한 파일은 기존 GCS 등 영구 저장소에 보존하고 DB에 위치를 기록한다. 임시 러너 파일이나 공급사 만료 URL만으로 복구를 설계하지 않는다.
- 실패한 요청의 과금 여부가 불명확하면 비용 예약을 유지한다. 상태 확인 없이 요청을 다시 보내거나 예산을 환급하지 않는다.

# 08 사실 검증과 자산 사용 기준

**주장 검증**

- 공식 수사기관·공공기록·당시 1차 자료를 우선한다. 언론 보도는 원출처와 독립성을 확인한다.
- 핵심 주장마다 URL뿐 아니라 근거 문장·문서 위치·확인 날짜를 남긴다. 여러 기사가 같은 보도를 인용하면 독립 출처 여러 개로 세지 않는다.
- LLM의 ‘확실하다’는 응답이나 두 모델의 동의만으로 검증 완료 처리하지 않는다.
- 원문이 일부 사실만 뒷받침하면 문장 전체가 확인된 것으로 처리하지 않는다. 보도된 주장은 출처를 밝혀 설명하고 가설은 사실과 분리한다.
- 생성 전 근거 확인과 생성 후 최종 주장 대조를 모두 수행한다. 제목·썸네일·설명란에만 생긴 과장도 차단한다.

**자산·품질 검토**

- 사진·지도·문서·음악·영상의 이용 조건을 개별 확인한다. Pexels를 무조건 CC0로 간주하거나 파일명만으로 라이선스를 통과시키지 않는다.
- 사건과 무관한 자료 영상은 분위기용 화면으로 표시하며 실제 현장·인물·증거처럼 제시하지 않는다.
- 인용·기록·지도·연대기 해설이 실제 내용을 전달하도록 구성한다. 저작권 허용과 유튜브 수익화 적합성은 별도로 검토한다.
- 발음·문장 누락·반복·잘린 음성·청크 연결·자막 동기화·음량·검은 화면을 실제 재생본에서 확인한다.
- 근거 부족·라이선스 불명·중복 의심·비용 초과·검토 미완료는 공개 차단 사유다.

# 09 제작 기술과 TTS 선택

GitHub Actions의 NestJS CLI → 사건·근거 등록 → 중복 판정·예약 → 근거 기반 대본 → 최종 주장 검증 → TTS·자산 → FFmpeg → 비공개 업로드 → YouTube Studio에서 사람 검수·공개·성과 확인 → 공개 상태 동기화.

- NestJS TypeScript는 src/에 두고 기존 npm 제작·롱폼 Phase 1/2 명령을 유지한다. React·PWA·HTTP 진입점과 전용 의존성·테스트·디자인 문서는 삭제한다.
- 사건·원문·주장·예약·자료 권리·과거 이력·실패 복구·비용 정산은 Actions의 JSON 관리 요청 또는 같은 CLI로 실행한다. 입력 형식·키 설정은 README와 worker-requests.md, .env.example에 기록한다. 실제 API 키는 Actions Secrets 또는 로컬 .env에만 둔다.
- 이전 롱폼의 1,200~1,400단어·2,200토큰 제한을 새 제작 경로에서 교체한다. 충분한 근거가 있을 때 최대 약 3,600단어를 목표로 생성하되, 실제 음성 길이에 맞춰 합성한다. 분량을 채우기 위한 반복은 허용하지 않는다.
- 현재 롱폼의 ‘LLM이 만든 사실 목록’은 검증 자료로 취급하지 않는다. 06~08절의 근거 수집·최종 검증 경로를 공통 적용한다.
- Shorts와 Long-form은 같은 NarrationProfile을 사용한다. 공급사·모델·화자·말하기 지시·속도·후처리 버전을 고정한다. 공급사별 속도 값이 같다고 실제 발화 속도가 같다고 보지 않는다.
- 장시간 렌더는 체크포인트와 타임아웃을 두고, 파일과 상태를 보존해 재개한다.

## Qwen3-TTS 로컬 실행 검토

교체 예정 GPU는 사용자 확인 기준 AMD Radeon RX 9060 XT 16GB다. 아직 GPU 교체 전이며, 이번 구현에서는 Qwen을 설치하거나 연결하지 않는다. AMD는 이 GPU의 Windows용 PyTorch 지원 경로를 제공한다. 이는 Qwen3-TTS의 해당 PC 실행·속도·음질이 검증됐다는 뜻은 아니다. [AMD 지원표](https://rocm.docs.amd.com/projects/radeon-ryzen/en/latest/docs/compatibility/compatibilityrad/windows/windows_compatibility.html)

검증 순서는 다음과 같다.

1. 확인된 VRAM 16GB를 기준으로 OS·드라이버와 사용 가능한 GPU 메모리를 확인하고 AMD 지원 조합의 ROCm/PyTorch 환경을 별도로 준비한다.
2. Qwen3-TTS-12Hz-0.6B-CustomVoice로 영어 짧은 음성 생성과 메모리·소요 시간을 확인한다.
3. 저음·차분한 말투 지시가 필요한 경우 1.7B-CustomVoice 또는 VoiceDesign을 비교한다. 저장소의 모델 표 기준 0.6B는 지시 기반 음성 제어를 지원하지 않는다.
4. 1분 원고와 롱폼 일부를 문장·문단 단위로 나눠 생성하고, 같은 음색·발음·누락·반복·연결 품질을 청취한다.
5. 별도 도입이 결정되면 모델·음색·참조 자료를 고정하고 NestJS 워커가 Python 음성 생성기를 호출해 결과를 FFmpeg 경로로 전달하도록 통합한다. 이번 구현에서는 진행하지 않는다.

공식 예제의 NVIDIA CUDA·FlashAttention 2 설정을 AMD에 그대로 적용하지 않는다. 검증 시작점은 AMD용 PyTorch와 호환되는 일반 attention 경로이며, 정확한 설정은 실행 검증에서 결정한다. 최소 VRAM이나 생성 속도는 측정 전 확정하지 않는다.

로컬 생성은 API 호출료가 없지만 전기·생성 시간·환경 관리 비용은 남는다. 표준 GitHub Actions 러너에 로컬 GPU가 연결되지는 않으므로, 우선 로컬에서 음성을 생성해 영구 저장소로 넘기는 방식으로 검토한다. 이때 PC가 꺼져 있으면 해당 작업은 대기한다. PC 없이 돌아가는 운영을 유지하려면 기존 API TTS 또는 별도로 과금되는 GPU 실행 경로가 필요하다.

정식 전환 전에는 현행 OpenAI onyx를 유지한다. Qwen 전환 시 채널 음색을 새로 확정하고 Shorts·Long-form에 함께 적용한다. 오류 때 다른 화자로 몰래 대체하지 않는다. 참조 음성은 권한이 확인된 자료만 쓰며, 기존 onyx 복제를 전제로 하지 않는다.

근거: [Qwen3-TTS 공식 저장소](https://github.com/QwenLM/Qwen3-TTS), [0.6B 공식 모델 카드](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-0.6B-CustomVoice), [GitHub 표준 러너 사양](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

# 11 장기 성장과 수익화

수익화는 콘텐츠와 시청자층이 쌓인 뒤 도달하는 단계다. 초기 성과를 월 50만 원 목표와 직접 비교해 실패로 판단하지 않는다.

성장 과정에서 확인할 것은 다음과 같다.

- Shorts: 시청 선택·넘김, 평균 시청 지속, 구독 전환, 관련 롱폼 유입.
- Long-form: 노출 대비 클릭, 평균 시청 지속 시간, 총 시청 시간, 재방문과 구독 전환.
- 운영: 영상별 실제 지출, 조사·검수·수정 시간, 보류 사유.
- 개선: 사건 선택·제목·도입·화면 구성 중 한 가지씩 바꾸고 비슷한 조건의 여러 영상에서 비교한다. 한 편의 급등·급락으로 방향을 확정하지 않는다.

유튜브 공식 안내의 2026.10.19 확인 기준:

| 구분 | 광고·Premium 수익화 신청에 필요한 수치 조건 |

수치 외 정책·지역·계정 요건과 심사를 충족해야 한다. Shorts 피드 시청 시간은 롱폼 시간 요건에 합산하지 않는다. 신청 시점의 YouTube Studio와 공식 기준을 다시 확인한다. [현행 YPP 안내](https://support.google.com/youtube/answer/72851?hl=en), [예정 변경 안내](https://support.google.com/youtube/answer/12843009).

|---|---:|

| $3.00 | 약 117,000회 |

위 계산은 수익화 이후의 예시이며 달성 시점 예측이 아니다. 월 1편씩 축적한 과거 영상의 조회도 합산한다. 월 $350 매출이 순수익 50만 원을 보장하지 않는다. 실제 원화 수입에서 API·외부 실행·저장소 등 운영비와 세금 영향을 반영하고, 본인 작업 시간은 따로 기록한다.

출처·저작권을 확보해도 템플릿에 의존한 반복 콘텐츠는 수익화에서 별도 평가된다. 각 사건의 고유한 기록과 해설을 영상의 중심에 둔다. [유튜브 수익화 정책](https://support.google.com/youtube/answer/1311392?hl=en).

# 12 단계별 장기 실행 계획

고정된 90일 마감은 두지 않는다. 아래 단계는 필요한 조건이 갖춰지면 진행하며, 기존에 가능한 제작은 계속한다. 수익 달성 기한을 정하는 일정표가 아니라 실행 순서다.

| 단계 | 실행 내용 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 1. 운영 기반 정리 | 기존 업로드·DB 이력 대조, 사건·콘텐츠 구분, 영구 중복 검사, 비용 예약, 업로드 결과 복구 보강 | DB 실패 시 차단, 동일 작업 중복 예약 차단, 업로드 응답 유실 시 재업로드 방지 확인 |
| 2. 검증된 제작 정착 | 출처 기반 대본과 생성 후 검증 공통 적용, 비공개 업로드·사람 검수, 공유 음성 프로필 | 최종 핵심 주장 근거 확인, 자산 권리 확인, 실제 영상·음성 검수 후 승인 가능 |
| 3. 콘텐츠 축적 | Shorts 주 3편·Long-form 월 1편 목표로 운영, 충분한 자료가 있는 사건부터 약 30분으로 확장 | 여러 편의 실제 비용·제작 시간·시청 반응을 비교할 기록 확보 |
| 4. 성장 개선 | 사건 선택·제목·도입·화면 구성 개선, Shorts와 롱폼 연결 효과 확인 | 개선 전후의 반복 관찰과 운영 가능한 제작량 확인. 약한 요소를 수정하며 지속 |
| 5. 수익화 진입 | 당시 YPP 조건과 정책 심사 충족, 실제 RPM·수입·운영비 확인 | 광고·Premium 등 실제 수익과 비용을 분리 집계 가능 |
| 6. 지속 운영 | 누적 영상의 장기 조회와 신작 성과 개선, 여러 달 순수익과 작업 부담 관찰 | 월 순수익 50만 원 수준과 감당 가능한 작업량을 함께 유지 |

성과 기록은 첫 발행부터 시작한다. 조회·시청 시간·평균 시청·구독 변화·CTR·Shorts 넘김·세부 유입은 YouTube Studio에서 확인한다. 별도 보드의 성과 집계·Analytics API 호출은 제거하고 없는 지표를 0으로 채우지 않는다.

Kling 3.0은 이번 제작 경로에 연결하고, Qwen3-TTS는 GPU 교체 후 별도 검증으로 남긴다. AI 장면을 모든 영상에 넣을 필요는 없다.

# 13 실행 우선순위와 완료 판단

| 우선순위 | 해야 할 일 |
|---|---|
| P0: 발행 전 필수 | 업로드 이력 대조·기존 이력 보존, 사건/콘텐츠 ID 구분, 원격 예약, 영구 중복 차단, 비용 상한, 업로드 결과 불명 복구, 최종 근거·권리·공개 승인 |
| P1: 제작 경로 보강 | Actions/NestJS 워커에 공통 검증 적용, 롱폼 장별 대본·실제 길이 대응, 음성·자막 QA, 첫 영상부터 비용·작업 시간·Studio 성과 기록 |
| P2: 도구 검증·개선 | GPU 교체 후 Qwen 실행·음질 비교, Kling 무음 5초 장면의 실제 품질·청구 확인, 제목·도입·연계 개선 |
| 필요 시 검토 | 대규모 공급사 추상화, 공개 다중 사용자 보드, 저장소 교체. 실제 문제가 확인된 경우에만 추진 |

구현 시 확인할 핵심 사례:

- 같은 사건의 다른 표기 → 기존 caseId에 병합하고, 고유한 새 각도는 허용.
- Shorts 이후 충분한 새 정보를 담은 롱폼 → 허용. 같은 대본의 반복·늘이기 → 차단.
- 생성 대본·제목에 근거 없는 주장이 추가됨 → 검증 실패로 공개 차단.
- DB 조회 실패·예약 충돌·예산 부족 → 유료 생성과 공개 차단.
- 업로드 성공 후 응답·저장 실패 → 결과 대조 전 재업로드 차단.
- 업로드 전 콘텐츠 변경 → 재검증·재렌더. Studio에서 공개한 뒤 동기화 → 기존 영상 ID로 published 기록, 중복 업로드 없음.
- Qwen 실행 실패 → 다른 화자로 자동 대체하지 않고 보류하거나, 사전에 정한 같은 프로필의 승인 경로만 사용.

최종 원칙: 새로운 사건이거나, 기존 사건에서 시청자에게 실질적으로 새로운 검증 정보·맥락을 제공할 때 제작한다. 같은 사건이라는 이유만으로 확장을 막지 않으며, 일정과 분량을 맞추기 위해 근거·품질 기준을 낮추지 않는다.

문서 상태: 2026.10.21 사용자 요청에 따라 보드를 제거하고 Actions 제작·YouTube Studio 검수/공개 흐름으로 수정한 장기 운영 계획. 가격·정책 확인일은 2026.10.19이며 도입·신청 시점에 재확인한다. NestJS 워커·Kling 3.0·Studio 상태 조회를 유지하고 .env.example을 현재 환경변수 기준으로 정리한다. 실제 .env 입력·수정, 운영 DB SQL 적용, 외부 서비스 인증·결제·발행, Qwen 연결·GPU 검증은 실행하지 않는다. 운영 및 검증 방법은 README를 따른다.
